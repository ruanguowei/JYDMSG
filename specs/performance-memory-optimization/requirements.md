# 小程序性能与内存优化需求

## 1. 目标

在不改变现有业务功能、页面入口、用户操作结果、云函数接口和数据语义的前提下，优化微信小程序前端与实际使用中的云函数，降低重复计算、重复请求、无效数据传输和页面长期驻留造成的资源占用，并排查潜在内存泄漏。

## 2. 范围

- `miniprogram/` 下已注册页面、公共组件、应用初始化与静态资源使用。
- `cloudfunctions/` 下被前端实际调用的独立云函数和 `quickstartFunctions` 聚合路由。
- 首页、预约、报名/查询/送件、专家评审、管理员、入围/获奖查询、作品画册等现行业务链路。
- 微信开发者工具与本地脚本的验证流程。
- CloudBase 生产环境允许部署本次优化涉及的云函数，但不写入或删除业务数据。

## 3. 约束与非目标

- 不改变现有页面视觉与交互语义，除非是修复明显卡顿或错误状态。
- 不删除、重命名或改变云函数现有入参/返回字段的含义。
- 不修改数据库集合结构、权限规则或生产数据；若后续发现确有必要，必须另行说明影响并确认。
- 不执行管理员数据清洗、排名生成、证书更新、批量复制或其他会重写业务数据的危险函数。
- 保留工作区中用户已有的未提交改动，不回滚、不整理、不覆盖无关内容。
- 未在 `app.json` 注册的旧页面和工具仅做静态审计；除非其代码被现行业务引用，否则不主动重构。

## 4. 用户故事

### 4.1 普通用户

作为小程序用户，我希望首页、报名、查询、送件和个人中心打开更快、交互更流畅，并且长时间浏览或反复进出页面后不会明显变卡。

### 4.2 专家和管理员

作为专家或管理员，我希望作品列表、作品详情、评分和结果页面在数据量较大时仍能稳定响应，不因重复请求或大对象渲染造成卡顿。

### 4.3 维护人员

作为维护人员，我希望优化后的前端与云函数保持接口兼容，部署后不需要迁移数据，并能清楚知道哪些风险已经修复、哪些需要真机观察。

## 5. 验收标准

### R1 功能兼容

- 当用户按现有入口完成任一业务流程时，小程序应保持原有导航、校验、提示、提交结果与数据语义。
- 当旧版本前端或现有页面调用被优化的云函数时，云函数应继续接受原入参并返回兼容字段。

### R2 请求与计算优化

- 当同一页面已有等价请求正在执行时，页面应避免无意义的并发重复请求。
- 当互不依赖的数据可并行加载时，系统应并行执行，并保持原有错误处理语义。
- 当页面只更新局部状态时，页面应避免把不相关的大对象重复传入 `setData`。
- 当云函数查询只需要部分字段或有限记录时，云函数应避免拉取无用的大字段或无边界全表数据。

### R3 内存与生命周期

- 当页面隐藏或卸载时，页面应释放其创建的定时器、监听器、音频/视频/Canvas/观察器等可释放资源。
- 当异步任务在页面卸载后返回时，页面不应继续执行不必要的 `setData` 或保留大对象引用。
- 当作品画册等大数据页面释放内存时，缓存、预览图片和媒体对象应按既有业务语义得到清理。

### R4 云函数稳定性

- 当云函数处理分页、批量写入或并发查询时，应设置合理边界，避免无控制并发和不必要的内存累积。
- 当云函数发生异常时，应保留现有可识别的错误返回，不通过空 `catch` 隐藏失败。

### R5 验证与发布

- 当本地修改完成后，相关 JavaScript/JSON 应通过可执行的语法或结构检查。
- 当改动涉及用户可见页面时，应使用微信开发者工具或预览码验证核心路径。
- 本次工作可以部署云函数，但不上传小程序体验代码、不提交审核或发布上线。

## 6. 完成定义

- 提交优化清单及每项改动的影响范围。
- 提交内存泄漏风险清单，区分“已修复”“未发现问题”“需要真机观察”。
- 完成相关本地检查、CloudBase 代码审查和可行的开发者工具/CI 验证。
- 交付本地修改并部署相关云函数，由用户在微信开发者工具和真机环境中验证小程序。
